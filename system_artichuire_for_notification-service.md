Notification Service — System Architecture Specification

Document Type: System Architecture Specification
Service: Notification Service
Architecture Style: Event-Driven Microservice
Primary Language: TypeScript / NestJS
Client API: GraphQL Federation
Durable Messaging: Kafka
Background Job Processing: BullMQ
Ephemeral State / Coordination: Redis
Persistent Data: PostgreSQL
Realtime Integration: NATS → Realtime Service → WebSocket
Containerization: Docker
Orchestration: Kubernetes
Local Kubernetes Development: Skaffold

---

1. Purpose

The Notification Service is responsible for reliably delivering notifications generated by business events across multiple communication channels.

The service must support:

Email
SMS
Push Notification
In-App Notification
Realtime Notification

The service is responsible for:

Event consumption
Notification creation
Notification preferences
Template resolution
Channel selection
Delivery scheduling
Background processing
Provider abstraction
Retry handling
Idempotency
Rate limiting
Delivery status tracking
Dead Letter Queue handling
Realtime notification integration
Observability

The Notification Service must not contain unrelated business logic such as:

Payment processing
Driver assignment
Delivery state management
Authentication
User management

Those responsibilities remain owned by their respective services.

6. Why Kafka + BullMQ?

Kafka and BullMQ have different responsibilities.

Kafka

Kafka represents:

Business facts

Examples:

delivery.created
delivery.driver.assigned
delivery.driver.accepted
delivery.picked_up
delivery.in_transit
delivery.completed
delivery.cancelled
payment.completed
payment.failed

Kafka provides:

Durability
Replay
Consumer groups
Event retention
Ordering
Multiple consumers
At-least-once delivery

---

BullMQ

BullMQ represents:

Work that needs to be executed

Examples:

send email
send SMS
send push notification
process notification
retry provider call
send scheduled notification
cleanup expired notifications

BullMQ provides:

Delayed jobs
Retries
Backoff
Concurrency
Job state
Worker processing
Failure handling
Job prioritization

Therefore:

Kafka
=
What happened?

BullMQ
=
What work must be executed?

7. Why Redis?

Redis is used by BullMQ and also provides coordination capabilities.

Redis responsibilities:

BullMQ backend

Redis must NOT be the source of truth for:

Notification history
Delivery status
User preferences
Notification templates
Business records

PostgreSQL remains the source of truth.

21. Kafka Partitioning

For events where notification ordering matters, use:

partition key = userId

Example:
user_123
   |
   +---- delivery.created
   +---- driver.assigned
   +---- delivery.started
   +---- delivery.completed

This helps preserve ordering for notifications associated with the same user.

If strict ordering is only required per delivery, use:

partition key = deliveryId

The exact partition strategy must be documented per event family.

24. Kafka Consumer Reliability

Kafka provides at-least-once delivery.

Therefore:

Same event may be consumed more than once.

The Notification Service must be idempotent.

Example:

Kafka Event
    |
    v
eventId = evt_123
    |
    v
Check notification_inbox
    |
    +---- EXISTS → Ignore
    |
    +---- NOT EXISTS
             |
             v
       Process Event
             |
             v
       Save inbox record

31. BullMQ Job Idempotency

Use deterministic job IDs.

Example:

notification:{notificationId}:channel:{channel}

This prevents duplicate queue insertion where appropriate.

However, BullMQ job deduplication is not a replacement for database-level idempotency.

Both layers should exist.

Retryable failures:

   |
   v

   |
Attempt 2
   |
   v

   |
Attempt 3
   |
   v

33. Exponential Backoff

Use:

delay = baseDelay * 2^attempt + jitter

Example:

1s
2s
4s
8s
16s

with random jitter.

This prevents a large number of workers from retrying simultaneously.

41. Why NATS for Realtime?

Kafka is durable.

NATS is low-latency.

A WebSocket notification does not necessarily need Kafka retention after the durable notification record already exists.

Therefore:

PostgreSQL
=
Durable notification

Kafka
=
Durable business event

NATS
=
Realtime fan-out

WebSocket
=
Browser delivery

---

42. Realtime Failure

If NATS/WebSocket fails:

Notification still exists in PostgreSQL.

The user can retrieve it through GraphQL.

Therefore realtime delivery is an optimization, not the only source of truth.
